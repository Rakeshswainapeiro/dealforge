# W4-01 - Portfolio register (ENT-04)

## What this delivers

The advisory synergy (W3-11) and conflict/concentration (W3-10) checks need a
single, tagged picture of what the group already owns. This builds that register
from the BRD ENT-04 company list and the Sirius subsidiary register, so each
record carries a **cluster**, a **sector**, a **geography** and a set of
**capability** tags rather than a bare name.

The fifteen BRD-named companies are the spine: Esyasoft, SAIF, Coredge, Infinia,
Finstreet, Derby, CMC, Sanimed, Atlas, Apeiro, Bayanat, Oxinus plus Judan, ADI
Chain and DDSC. Twelve of those resolve to a record in the Sirius subsidiary
register and inherit their sector, geography and capabilities from that entity's
registered nature of business. The three that sit outside the Sirius subtree
(Judan, ADI Chain, DDSC) are carried from the BRD list and flagged as BRD-named
with a note that their tags await client confirmation (open decision Q6).

The register is versioned configuration in an AppSettings record, the same
pattern as the scorecard and quality score. The shipped register is
`PR-01.1`; an administrator edits the cluster tags inline or loads the register
back from a CSV template, and each save mints the next revision (`PR-01.N`) with
an audit event recording the added, removed and edited records.

## How it works

1. `GET /api/portfolio-register` returns the effective register plus its
   validation report and the shipped defaults (any authenticated reader).
2. `GET /api/portfolio-register/template.csv` serves the load template (BRD
   ENT-04 - the register must be loadable from a template).
3. `PUT /api/portfolio-register` requires the admin / configurator role
   (`canConfigure`). `buildPortfolioRegister` validates the payload (at least one
   company, unique names, a known cluster, a sector, a valid status), mints
   revision + 1 and persists it. An invalid payload is refused with a 400 and the
   list of errors.
4. `POST /api/portfolio-register/import` parses the CSV template into the same
   payload and saves it the same way.
5. `GET /api/portfolio-register/matches?sector=&geography=&capabilities=`
   exposes the sector, geography and capability-overlap matches the synergy and
   conflict checks consume, so the screening board can name the affected
   companies.
6. `loadPortfolioRegisterConfig` resolves the stored record for the panel, the
   fields endpoint and the pipeline; a missing or invalid record falls back to
   the shipped register so a screen never depends on a row.

## Validation

- `node --test server/tests/portfolioRegister.test.js` - 16 pass (shipped shape
  of 15 companies each with a sector/cluster/geography, the BRD-only flagging,
  duplicate / unknown-cluster / missing-sector refused, revision minting,
  resolve fallback that keeps the stored revision, diff added/removed/edited,
  the CSV template round-trip, and the sector / geography / capability matches).
- `BASE_URL=http://localhost:34099 node --test server/tests/m3.test.js` - 53
  pass. The W4-01 case proves a reader sees the fifteen companies and the
  template, a deal-lead gets 403 on a write, an admin edit advances the revision
  and the matches endpoint reflects the tags.
- `npm run build` and eslint clean on the touched files.

## Notes

The register is generated by `scripts/generate_portfolio_register.mjs` from the
Sirius subsidiary register and the nature-of-business map, so a change to the
source tree can be reflected by re-running the generator. Evidence captured
against the demo stack at http://localhost:34010 from the mvp seed profile.
